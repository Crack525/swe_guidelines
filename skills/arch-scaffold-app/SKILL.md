# arch-scaffold-app

Follow `${CLAUDE_SKILL_DIR}/../_shared/scaffold-conventions.md` first.
Sections that shape this skill: 12 (Apps), 15 (Client App
Architecture), 10 (Clients Live in One Place, Realtime at the Edge) of
`${CLAUDE_SKILL_DIR}/../../architecture.md`.

## Input

`$ARGUMENTS`: `<app-name> --kind portal|admin|cli`.

- `portal`: the product's browser app with the realtime channel.
- `admin`: the operator console: same stack and design kit, no realtime
  socket, routes under `/v1/admin/*`, its own origin.
- `cli`: a Python command-line app over REST.

## Files for a browser app

Under `apps/<app-name>/`:

| File                             | Holds                                                                    |
|----------------------------------|--------------------------------------------------------------------------|
| `package.json`, `tsconfig.json`, `vite.config.ts` | the workspace package, strict TypeScript, the Vite build       |
| `openapi.json`                   | the committed contract, regenerated by the repository's `openapi` target |
| `src/api/schema.d.ts`            | generated from `openapi.json` (never hand-edited)                        |
| `src/api/types.ts`               | the curated facade: `export type XView = Schemas['XView']`               |
| `src/api/client.ts`              | one transport client: bearer, app header, error envelope, request id, 401 handling |
| `src/queries/keys.ts`, `src/queries/<domain>.ts` | the query-key factory and one hooks module per domain    |
| `src/realtime/{RealtimeProvider.tsx,envelopes.ts,router.ts,timeouts.ts}` | portal only: the one socket, the discriminated union, the cache router, pinned timeouts |
| `src/features/<screen>/{<Screen>Page.tsx,use<Screen>Vm.ts,<screen>Model.ts,<screen>Model.test.ts}` | one starter screen in the three-layer split |
| `src/app/{App.tsx,routes.tsx,RequireAuth.tsx}` | the shell and the sign-in gate (`RequireAdmin.tsx` for the console) |
| `README.md`                      | the app's conventions in one page                                        |

## Files for a CLI

Under `apps/<app-name>/`:

| File                                   | Holds                                                           |
|----------------------------------------|-----------------------------------------------------------------|
| `pyproject.toml`                       | the distribution and the console entry point                    |
| `src/<root>/apps/cli/main.py`          | the command groups, one per namespace                           |
| `src/<root>/apps/cli/client.py`        | one HTTP client: bearer from the environment, app header, error envelope, OS trust store |
| `src/<root>/apps/cli/follow.py`        | submit-and-follow for long operations, exit code from the outcome |
| `tests/test_cli.py`                    | commands over a stubbed client                                  |

## Procedure

1. Browser app: mirror the existing app's design tokens, component kit,
   and sign-in flow when one exists; copy, never fork the API client.
   Feature code never calls `fetch` and never imports `schema.d.ts`.
2. Portal: every realtime envelope routes into the query cache; the
   provider owns reconnection, backoff, and the degraded polling mode.
3. Console: no socket, no tenant context, the sign-in flow of the
   portal, the operator gate on the client rendered from the API's own
   refusal.
4. CLI: creating calls send `Idempotency-Key`; followed operations poll
   at a fixed cadence and exit non-zero on failure.
5. Run the app's lint, typecheck, and tests.

## Output

The file list and command outcomes, as the conventions state.
